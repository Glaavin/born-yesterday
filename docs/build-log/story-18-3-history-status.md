## Why DEFAULT 'ok' is correct rather than a guess

This is the part that looks arbitrary in six months without the derivation, so it is recorded in full.

Every pre-existing row was written by the *old* `signalsToHistory`, which filtered:

```ts
.filter((s) => s.valueText != null || s.valueNum != null)
```

Therefore, by construction: **every existing row had a value ⇒ its check demonstrably completed ⇒ `status = 'ok'` is provably true of it.** The backfill is not an assumption about old data; it is a consequence of the filter that produced it.

**Verified empirically against the live database after migrating**, not merely argued:

```
column      : status | text | NOT NULL | default 'ok'
constraint  : present
distribution: [{"status":"ok","n":748}]
pre-existing VALUELESS rows (must be 0): 0
total rows  : 748
```

Zero valueless rows is the measurement that confirms the derivation.

**The window closes the instant the writer changes.** Once valueless rows are written, `value IS NULL` no longer implies anything about whether the check ran, and no later migration can reconstruct it. That is why the ordering below is a requirement, not a preference.

## Sequencing (deliberate, two steps, not one)

1. Migration applied to Neon — **confirmed** by the query above.
2. Only then the writer change ships.

Run as one step, an insert could hit `NOT NULL` before the column exists; worse, the backfill proof depends on no valueless row existing at migration time.

## Why every signal is recorded, not just `ok` ones

The narrower option — record `ok` rows only — fixes "DMARC absent vs. not checked" but **not** the failure that prompted this:

> A domain that had DMARC and then hits a DNS timeout writes **no row**. The Phase-2 "what changed" digest reads that gap as *"DMARC was removed"* — a false change event generated by a network hiccup.

Under the chosen option that is a `failed` row, and the diff correctly reports that nothing happened. History records what was true when, and *"we didn't look"* is part of what was true.

**Cost, accepted:** ~26 rows per refresh vs ~16, about +62%. Noise at MVP scale. The 10k-domain projection (~13.5M rows/year vs ~8.3M) describes a scale where a retention policy is a real conversation regardless — choosing lossy history to defer a question we will answer anyway is the wrong trade.

## Decisions & deviations
- `status` is `text` + CHECK rather than a PG enum, mirroring the `reports.skepticism_state` precedent from 0001 (additive-forward; a new enum value would otherwise need `ALTER TYPE`).
- `schema.ts` imports `SignalStatus` from `signals/types.ts`; both directions are `import type`, so there is no runtime cycle.
- No reader changes: `countSignalHistory` is the only reader today. The Phase-2 digest is the consumer this exists for.

## Follow-ups / tech debt
- No index covers `status`. A "what changed" query filters on `(domain, captured_at)`, which `idx_signal_history_domain` already covers. Revisit if the digest queries by status.
- Retention/partitioning is unaddressed and becomes real well before 10k domains on weekly refresh.
